# 実装issueの作成・着手前レビュー指針

この文書は、TBX / TBX Next の実装issueを作成するとき、および実装着手前にissueを再評価するときの既定の確認観点をまとめる。

issue本文の正式な構成は、プロジェクトで定めている実装issueテンプレートに従う。この文書はテンプレートを置き換えるものではなく、**issueの粒度、設計確定性、検証可能性を判断するための補助基準**とする。

重要な設計判断はADR、現在の実装事実はコードとテストを正本とし、この文書だけを仕様の根拠にしない。

## 1. 作成時の考慮事項

### 1.1 実装単位

実装issueは、原則として一つの変更理由と一つの完成状態で説明できる単位にする。

次を確認する。

- 1 issue - 1 PRで、単独で実装・レビュー・検証できるか。
- 異なる変更理由、異なる完成条件、または独立して回帰確認できる変更を一つに混在させていないか。
- 共通の低水準能力と、それを利用する高水準機能が独立して検証可能なら分離できないか。
- runtime能力、hostまたはCLIとの接続、利用者向け構文、サンプル、文書整備が、それぞれ独立した完成条件を持っていないか。
- 大量の機械的変更やテスト移動であっても、レビュー可能性を損なう規模なら、契約上または機能上のまとまりごとに段階分割できないか。
- 分割したissueの前提関係と実装順序が明示されているか。

分割によって一時的に無効な状態を `main` に導入する場合や、単独では検証不能になる場合は、無理に分割しない。

### 1.2 設計の確定状態

実装者が、新しい重要な設計判断を行わなくても着手できる状態にする。

次を確認する。

- 必要な意味論、責務分担、公開契約、失敗時契約、名前解決、所有主体その他の重要な判断が、採用済みADR・仕様・既存実装から一意に導けるか。
- 実装者が複数案から重要な方針を選ばなければならない状態を残していないか。
- 重要な未決定事項がある場合、実装issueへ埋め込まず、ADR issueまたは調査・計画issueへ分離すべきではないか。
- 採用済みの設計判断と、実装者へ委ねる内部実装詳細を区別しているか。
- 既存ADRと現在のコード・テストが矛盾している場合、どちらかを暗黙に正しいものとしていないか。

### 1.3 変更対象と対象外

変更対象は、可能な範囲でcrate、module、主要ファイル、既存の型・関数・テスト群、または利用者向け経路の単位まで具体化する。

同時に、次も明記する。

- 今回変更しない隣接機能。
- 変更しない公開API、CLI、構文、設定、ログ、fixture、保存形式。
- 実装中に便乗して変更されやすい事項。
- リファクタリングの場合、移動・分割するものだけでなく、元の場所へ残す責務。

対象外を列挙する目的は、将来の変更を禁止することではなく、今回のPRの完成条件を限定することである。

### 1.4 維持する契約

「既存挙動を壊さない」だけで済ませず、必要に応じて何を維持するか具体化する。

特に次を確認する。

- 正常系だけでなく、失敗、途中終了、入れ子、継続、完了、復帰、再実行その他の主要経路。
- 原子性または失敗時状態が重要な処理では、変更してはならない状態。
- リファクタリングでは、観測可能な実行結果、公開可視性、diagnostic、source mapping、error kind、primary span等。
- テスト移動では、既存test関数名、assert、fixture、期待値等のうち維持すべきもの。

抽象的な契約や、コードだけから設計理由を理解しにくい制約は、必要に応じて対応するソースコードの近くへコメントとして残す。

### 1.5 受け入れ条件

受け入れ条件は「何を実装するか」の言い換えではなく、完成後に成否を客観的に判断できる状態として記述する。

次を確認する。

- 正常系の代表ケースがあるか。
- 主要な無効入力や失敗経路があるか。
- 原子性、部分更新防止、後続処理の抑止等が必要なら独立した条件になっているか。
- 既存の回帰点が明示されているか。
- 「適切に」「問題なく」「対応する」等、確認方法が不明な表現だけになっていないか。
- 新しい契約の確認を「既存テストが通る」だけで代用していないか。

分割・移動を目的とするissueでは、対象が移動したことに加えて、消失、重複、意図しない可視性変更、本番コードへの便乗変更がないことも確認する。

### 1.6 テスト方針

各受け入れ条件を、どの種類のテストまたは確認方法で検証するか対応付けられる内容にする。

- unit testだけで確認できない利用者向け経路は、必要に応じてintegration testまたは実バイナリE2Eまで含める。
- host接続、CLI、I/O、乱数その他の外部能力を扱う場合は、コア能力のテストと製品経路の接続テストを区別する。
- 挙動不変を目的とするリファクタリングでは、変更前後のtest名、期待値、test一覧等を比較する方法を必要に応じて指定する。
- 正常系だけでなく主要な失敗経路も確認する。

### 1.7 内部実装詳細を固定しすぎない

実装issueでは、必要な変更内容と守るべき制約を示す。

一方、ADRまたは仕様で決定済みでない次の事項は、原則として実装者に委ねる。

- private型の具体的構成。
- private関数の分割方法。
- 内部helper名。
- 子moduleの具体的なファイル名や分割数。
- 同等の契約を満たす複数の内部実装方法。

issueが実装手順書になりすぎて、より小さく明確な実装を妨げないようにする。

### 1.8 現在の `main` への再照合

issue作成後に時間が経過した場合や、前提となるissue / PRが進んだ場合は、着手前に現在の正本へ再照合する。

少なくとも次を確認する。

- `main` の現在のコード。
- 関連テスト。
- 採用済みADR。
- 完了した前提issue / PR。
- 対象moduleや公開APIの変更。
- issue本文に記載された前提が置換済みになっていないか。

古いissue本文を現在の実装より優先しない。

## 2. issue分割を検討する条件

次のいずれかに該当する場合は、原則としてissue分割を検討する。

- 一部だけでも独立した有用な基盤または完成状態になる。
- 前半と後半で主な変更対象moduleまたは責務が異なる。
- コア能力とhost・CLI・製品経路の接続が混在している。
- 言語意味論の決定とその実装が混在している。
- 本番コード変更と大規模なテスト再配置が混在している。
- リファクタリングと観測可能な挙動変更が混在している。
- PRレビュー時に一つの論点として妥当性を判断するには差分が大きすぎる。
- 後半の実装可否が前半の実装結果によって初めて確定する。
- 同じissue内で別々の受け入れ条件群・別々のテスト戦略が必要になっている。

分割後は、各issue単独で検証可能であることと、前提関係が追跡可能であることを確認する。

## 3. 着手前レビューの既定観点

実装issueを作成または着手前に再評価するときは、少なくとも以下を確認する。

1. **設計確定性**  
   実装者が新しい重要な設計判断を行わなくても着手できるか。

2. **一つの変更理由**  
   issue全体を一つの変更理由と一つの完成状態で説明できるか。

3. **PRとしての規模**  
   1 PRとしてレビュー可能な差分になるか。

4. **前提関係**  
   必要なADR、先行issue、既存実装、テストが明示され、実装順序が分かるか。

5. **対象範囲の具体性**  
   何を変更するのかがmodule、責務、既存シンボルまたは利用者向け経路の単位で特定できるか。

6. **対象外の十分性**  
   実装中に自然に手を出したくなる隣接事項が整理されているか。

7. **実装上の制約**  
   依存方向、原子性、公開可視性、名前解決、状態変更順序その他の重要な制約が明示されているか。

8. **受け入れ条件の検証可能性**  
   各条件について、実装完了時に成否を客観的に判断できるか。

9. **失敗経路**  
   無効入力、途中失敗、外部能力失敗、部分更新防止その他の主要失敗経路が扱われているか。

10. **回帰範囲**  
    公開API、CLI、binding、source mapping、diagnostic、fixture、保存形式、標準ライブラリ、既存サンプル等への影響が必要に応じて確認されているか。

11. **テストとの対応**  
    受け入れ条件を一項目ずつテストまたは確認方法へ対応付けられるか。

12. **リファクタリング固有の確認**  
    挙動不変を目的とする場合、維持するtest名、assert、可視性、diagnostic、mapping等が明示されているか。

13. **実装詳細の過剰指定**  
    ADRで決定されていないprivate型、関数分割、内部API等までissueが固定していないか。

14. **正本との最新整合**  
    issue作成後に `main`、関連ADR、先行PRが変化していないか。

## 4. 問題を見つけたときの扱い

レビューで問題が見つかった場合は、単にissue本文を詳しくすることを既定の解決策にしない。

原因に応じて次から選ぶ。

- **既に決定済みの前提が本文から不足している**  
  既存ADR・仕様・実装への参照と必要な制約を本文へ追記する。

- **実装範囲が大きすぎる、または異なる完成状態が混在している**  
  複数の実装issueへ分割する。

- **重要な設計判断が未決定である**  
  ADR issueへ分離する。

- **現在の状態確認、選択肢比較、移行計画が先に必要である**  
  調査・計画issueへ分離する。

- **既存issueと重複、置換、前提関係の変化がある**  
  正本となるissueを明確にし、関連issue間の関係を更新する。

## 5. 過去の再評価から得た代表例

この文書の観点は、特定issueの内容を一般仕様化するものではないが、次のような再評価パターンを背景としている。

- #1686 と #1696: 高水準 `PRINT` と低水準出力基盤を分離した。
- #1688 と #1689: runtime入力能力とCLI側stdin接続を分離した。
- #1690 と #1695: session所有の乱数能力と製品実行時のseed接続を分離した。
- #1817、#1822、#1823: 大規模なsource processor単体テスト移動を契約群ごとに段階分割した。
- #1819 と #1820: source processorの異なる変更理由を別の本番責務分割issueにした。

これらは「常に同じ分け方をする」という規則ではなく、独立した完成条件・変更理由・検証方法がある場合に分割する判断例として扱う。
