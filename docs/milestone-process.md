# マイルストーン完了時のクイックリファレンス確認

TBX または TBX Next のマイルストーンを完了する前に、そのマイルストーンで追加・変更したユーザー向け構文、標準語彙、入出力、CLI、実行方法、主要な注意事項が対象クイックリファレンスに反映されているか確認する。

対象は現行 TBX が [`tbx-quickref.ja.md`](tbx-quickref.ja.md)、TBX Next が [`next/tbx-quickref.ja.md`](next/tbx-quickref.ja.md)。実装・テスト・ADR・仕様を正本とし、クイックリファレンスは実装済み内容の実用的な入口として扱う。

## 計画と更新

- マイルストーンを新規作成または再整理するときは、原則として最後にクイックリファレンスとの整合性を確認し、必要なら更新する文書整備 issue を配置する。
- 未反映の内容があれば、原則としてこの文書整備 issue（種別: 実装）でクイックリファレンスを更新する。
- 各機能 issue で毎回更新することは原則必須としない。同一マイルストーン内で仕様や実装が変化する間に記述が繰り返し揺れるのを避け、最後にまとめて確認するためである。ただし、途中で明らかな誤情報になる場合など、早期更新が必要なときは個別 issue で対応し、その影響を記録する。

## 完了記録

変更が不要な場合も、確認結果を文書整備 issue に記録する。マイルストーン全体を管理する個別 issue がある場合は、そこへ記録を集約してもよい。

## マイルストーン識別と所属管理

TBX独自のマイルストーン識別子には `M<number>` 形式を使う（例: `M23`、`M24`）。GitHubでは `#<number>` がissue参照として解釈されるため、新しい文書では `Milestone #23` のように記述せず、`M23` と記す。

TBXのマイルストーン管理にはGitHubのMilestone機能を使わない。正式に採用したマイルストーンに属するissueには、その識別子と同名のissueラベルを付け、所属issueの集合を追跡する。計画issue、関連するADR、実装issue、completion review、最後のクイックリファレンス確認・更新issueには、いずれも同じ `M<number>` ラベルを付ける。

マイルストーンの目的、対象範囲、完了条件は計画issueを正本とする。ラベルは所属issueを識別するためのものであり、目的・完了条件・依存順を定義するものではない。クイックリファレンス確認・更新issueを最後に置く運用は、上記「計画と更新」に従う。

将来候補のissueには、正式にマイルストーンとして採用する前に番号や `M<number>` ラベルを割り当てない。採用時に次の連番を割り当て、計画issueとその時点で特定した所属issueに同名ラベルを付ける。候補の採用前に番号を先行割当しないことで、未確定の候補が順序や計画単位として扱われるのを避ける。
